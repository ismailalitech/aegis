Zynq UltraScale+ endpoint, phase B of docs/zynqmp-key-design.md: a key bound to this chip's PUF, without eFUSEs,
19 November 2026. LAN addresses masked; no key, IV or helper-data value appears here (they stay on the Windows
build PC, C:\tz\aegis-keys, owner-only).

1. PUF registration in boot-header mode (endpoints/zynqmp/windows/puf; AMD's xilskey example over JTAG)
   eFUSE guards: switches checked in the compiled header (only XSK_PUF_INFO_ON_UART TRUE), write APIs made
   uncallable at compile time, ELF call-graph check (writers linked but unreachable), and a read-only eFUSE snapshot
   that refuses unless CHASH, AUX, REG_DIS, SYN_WRLK and SYN_INVLD are blank. The first try stopped on PUF_MISC
   bit 28: XSK_ZYNQMP_EFUSEPS_PUF_MISC_RESERVED, set on this chip from the factory (read again with Linux up), which
   xilskey's own access check ignores; the guard now logs it.
   App: "PUF Registration Completed", syndrome (3088 hex), AUX, CHASH, shutter 0x0100005E, black key (64 hex), IV
   (24 hex); the red key print removed from the app. Parser: helperdata 1544 bytes, black key 32, IV 12.
   eFUSE cache before the run and after a power cycle: 44 registers identical (EFUSE_UNCHANGED; IPDISABLE left out,
   its VCU bit is valid only once the PL is configured).

   "Failed to calculated montgomery reduction in BN_MONT_CTX_set", while reading its own keys)

   header, 4K mode, boot-header RSA authentication, no auth_only); FSBL and PMU firmware encrypted, the rest plain;
   the red key absent from the image; bootgen -verify: header and FSBL signatures verified.
