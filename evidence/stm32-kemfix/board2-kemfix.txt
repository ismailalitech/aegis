## Deployment
1. Backup under reset: both 2 MiB flash views and the option bytes (backups/stm32h573/20261118-100835-board2-before-kemfix,
   checksummed); its secure slot is byte-identical to the running build, so restore_from_backup.sh rolls back.
2. Policy for stm32h573-dk-2 only: new SPE added beside the old one (board 1 is not connected and keeps its value).
3. tfm_s_signed.bin written to the secure slot (0x0C038000), ST-LINK chosen by serial: "Download verified successfully".
4. Admitted; then the old SPE removed from the policy: still admitted, so the board runs the new image. The pinned key
   is unchanged (it comes from the chip's DHUK, not from the image).
5. A reset of the board to make the gateway provision a new session, captured on the gateway (tcpdump on port 7444).

(between heartbeats 3 and 4):
  with no exchange pending              -> ERR pq -137   (PSA_ERROR_BAD_STATE)
  after a new PQKEMINIT (PQKEMEK, 9009 bytes back) -> ERR pq -149   (PSA_ERROR_INVALID_SIGNATURE: the credential names
                                                                    another encapsulation key)
The gateway's session was not replaced: heartbeats 4, 5 and 6 of the same session follow in the journal above.
The unfixed code accepts this replay (the seed replay-after-new-init, run on the PC against the committed source:
"ORACLE: credential accepted, but the model says invalid"); on the board it would have replaced the session with a key
the gateway does not share. It was not flashed back to show that.
