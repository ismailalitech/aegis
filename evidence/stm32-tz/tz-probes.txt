STM32H573I-DK board 2, TF-M v2.3.0 with the Aegis partition (SPE 3cacd9d0...), 18 November 2026.
TrustZone negative tests from the non-secure side (endpoints/stm32h573/probe.sh) and the partition's stack depth.

1. Can non-secure code use the DHUK? probe.sh --saes: a test image of the non-secure prover runs the partition's
   own key derivation (AES-256-ECB under the DHUK in SAES, the ML-DSA seed label) from the non-secure world.
   SAES-DHUK: refused (aegis-saes: init=0 encrypt=1 sr=0x00000000); TZIC SR1-4: 00000000 00000000 00080000 00000004
   GTZC TZSC1 (secure view): SECCFGR3 = 0x000C0000, so RNG (bit 18) and SAES (bit 19) are secure; PRIVCFGR3 =
   0x00040000. TZIC1 SR3 bit 19 is SAES's illegal-access flag. HASH, PKA and AES are left non-secure; the secure
   side does not use them (its crypto is in software).

2. Non-secure reads (one probe image per line; "secure value" read first over SWD, which sees the secure view)
   NS_FLASH 0x08088000: no read (fault: 23 attempts, 23 boots); TZIC SR1-4: 00000000 00000000 00000000 00000000
   S_FLASH_S 0x0C038000: no read (fault: 23 attempts, 23 boots); TZIC SR1-4: 00000000 00000000 00000000 00000000
   S_FLASH_NS 0x08038000: no read (fault: 23 attempts, 23 boots); TZIC SR1-4: 00000000 00000000 00000000 00000000
   S_SRAM_S 0x30032E00: no read (fault: 23 attempts, 23 boots); TZIC SR1-4: 00000000 00000000 00000000 00000000
   S_SRAM_NS 0x20032E00: no read (read as zero; secure value 0x30032E09); TZIC SR1-4: 00000000 00000000 00000000 01000004
   SAES 0x420C0C00: no read (read as zero; secure value 0x00000000); TZIC SR1-4: 00000000 00000000 00080000 00000004
   RNG 0x420C0800: no read (read as zero; secure value 0x00000000); TZIC SR1-4: 00000000 00000000 00040000 00000004
   NS_CODE 0x08088400: control, readable as expected: 0x20022800 (the same word over SWD); TZIC SR1-4: 00000000 00000000 00000000 00000004
   Reading the lines:
   - "fault": the read never returns. TF-M resets the chip and the prover boots and probes again (23 times in 40 s).
     This is the outcome for the secure aliases (SAU) and for the secure part of the flash through its non-secure
     alias.
   - "read as zero": the GTZC returns zero for a secure block and sets its illegal-access flag. TZIC SR4 bit 24 is
     SRAM1, and SR3 bits 19/18 are SAES/RNG. SRAM1's real word there is 0x30032E09 (attest_key_hash).
   - The FLASH flag (SR4 bit 2) is set on every boot, the control's included, so it does not come from the probes.
   - After a fault the flags read zero: the reset clears them.
   - NS_FLASH 0x08088000 (the non-secure slot's MCUboot header) also faults: the SAU's non-secure code region starts
     after the header. So the control is a word of the non-secure code (0x08088400, the initial stack pointer).
   After the tests the normal prover (NSPE 34637a4e...) was written back, and the gateway admitted the board again:
     19:04:53 stm32h573-dk-2 ADMITTED  [credential: issued session 6fc6a2807947...]
     19:05:27 stm32h573-dk-2 ADMITTED  [credential: valid, heartbeat 1 (uptime_s=62;link=1;fw=0.5.0)]

3. Stack depth of the Aegis partition (tfm_sp_aegis_pq_stack, 0x30041780, 26624 bytes), read over SWD after an
   attestation, an ML-KEM provisioning and a heartbeat. The stack is zero at reset and grows down, so the lowest
   non-zero byte bounds the deepest use:
     first non-zero byte at offset 7536: at least 19088 of 26624 bytes used (72%)
   TF-M's stack limit register faults before an overflow reaches other memory.
